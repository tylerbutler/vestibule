      <h2>Route request and callback phases</h2>
      <p>
        Register the strategies once. Initialize the state store once. Then
        route the request and callback paths to the middleware.
      </p>
      <p>
        <strong>What to notice:</strong> the request route stores temporary
        callback data and starts the redirect. The callback route returns an
        auth result only after state and PKCE validation.
      </p>
      <CodeBlock code={wispCode} lang="gleam" />

      <ul className="responsibility-list" aria-label="Middleware responsibilities before redirecting">
        <li>
          <strong>Initialize the state store once.</strong>
          Reuse the store so that middleware can bind callback data to the user
          flow.
        </li>
        <li>
          <strong>Let middleware consume callback data.</strong>
          After state validation, middleware removes the stored values before
          token exchange. A malformed callback or state mismatch does not
          remove a valid login session.
        </li>
        <li>
          <strong>Map <code>auth.uid(auth)</code> to your own account.</strong>
          Vestibule authenticates the provider identity. Your app manages user
          accounts and sessions.
        </li>
      </ul>

      <div className="scope-note">
        <strong>Using Mist?</strong> The route shape is the same. Use{" "}
        <a href="/docs/packages/mist">vestibule_mist</a> for plain Mist
        handlers.
      </div>
    </div>
  </div>

      <span>
        <span className="path-label">Advanced path for custom routing</span>

        <small>Choose this when you handle routing, sessions, and callback storage yourself.</small>

    <div className="path-body">
      <p>
        Core returns the authorization URL, state, and PKCE verifier. Your app

      </p>
      <CodeBlock code={coreInstallCode} lang="toml" />

      <h2>Handle the two phases yourself</h2>
      <p>
        Before the redirect, store{" "}
        <code>authorization_request.state(auth_request)</code> and{" "}
        <code>authorization_request.code_verifier(auth_request)</code>. Then
        redirect to <code>authorization_request.url(auth_request)</code>.
        Supply the stored values during callback validation. Delete them after
        a successful callback.
      </p>
      <p>
        <strong>What to notice:</strong> use an assertion only when you create
        the authorization request. A callback can be stale or forged. The
        provider can also reject it. Handle each error result.
      </p>
      <CodeBlock code={coreCode} lang="gleam" />

      <ul className="responsibility-list warning" aria-label="Core flow responsibilities">
        <li>
          <strong>Store state and PKCE verifier server-side before redirecting.</strong>
          Bind the values to the user's session. Set a short expiration time.
        </li>
        <li>
          <strong>Do not reuse stored callback data.</strong>
          Delete the stored values after a successful callback. Expire unused
          values quickly. A state mismatch must not delete a valid login
          session.
        </li>
        <li>
          <strong>Never assert the callback result.</strong>
          A stale tab, denied consent, a network error, or a forged state value
          can occur at run time.
        </li>
      </ul>
    </div>
  </details>

<section id="callback-failure">
  <h2>When the callback fails</h2>
  <p>
    Many callback failures are harmless. Examples include a stale tab, use of
    the back button, or a reused link. A forged <code>state</code> value is
    hostile. Vestibule returns a typed error for each failure, so your app can
    respond without a crash.
  </p>

  <p>
    <strong>What to notice:</strong> stop the current OAuth flow after a
    failure. Offer a retry only for a temporary upstream error. Never retry a
    state mismatch with the same callback data.
  </p>
  <CodeBlock code={callbackFailureCode} lang="gleam" />

  <div className="content-grid">
    <div>
      <h3>Why a callback fails</h3>
      <ul className="check-list">
        <li><strong>StateMismatchKind</strong>: The state is wrong or missing. This can indicate CSRF.</li>
        <li><strong>ProviderKind</strong>: The provider rejected the request. For example, the user denied consent.</li>
        <li><strong>MissingCallbackParamKind</strong>: The provider omitted a required value.</li>
        <li><strong>NetworkKind / CodeExchangeKind</strong>: A temporary upstream problem occurred.</li>
      </ul>
    </div>
    <div>
      <h3>How to respond</h3>
      <ul className="check-list warning">
        <li>Discard the failed callback. Do not reuse its parameters.</li>
        <li>Restart the flow after a stale tab, reused link, or state mismatch.</li>
        <li>Offer a retry only for a temporary network or code-exchange failure.</li>
        <li>Log the specific error on the server. Show users a generic sign-in error.</li>
      </ul>
    </div>
  </div>

  <div className="scope-note">
    <strong>Do not expose the error.</strong> The <code>reason</code> can
    contain internal details. Log it on the server and return a generic message
    to the browser.
  </div>
</section>

<section id="security-responsibilities" className="security-callout">
  <div>
    <h2>Before shipping</h2>
    <p>
      Complete these checks before you enable sign-in for users. Keep OAuth
      callback data on the server. Give the data a short expiration time and
      bind it to the user's session. Reject missing or mismatched callbacks.
    </p>
  </div>
  <ul className="check-list">
    <li>Production redirect URIs must use HTTPS.</li>
    <li>Store state and PKCE verifier values on the server for a short time.</li>
    <li>Remove client secrets, authorization codes, and PKCE verifiers from logs and error reports.</li>
    <li>Bearer tokens must be redacted from logs and error reports.</li>
    <li>A cookie-secret change invalidates OAuth callbacks that are in progress.</li>
  </ul>
</section>
